# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpenBomber is a Bomberman-style 2D game in C++17 with OpenGL 3.3 core (GLFW + GLAD + GLM, stb_image for textures), written for a university course on graphics processing fundamentals. Commit messages are written in Portuguese.

Current state: a 19×19 map with an unbreakable border, unbreakable pillars on even (x, y) and ~30% random breakable walls (the player's corner `(1,1)`, `(1,2)`, `(2,1)` is kept clear). One player moves continuously (WASD/arrows) and faces the direction of movement; Space places a bomb (one at a time) snapped to the nearest tile. A bomb explodes after 3 s into a plus-shaped fire of range 1 that lasts 1 s; fire skips unbreakable walls and the outside of the map, and destroys breakable walls. Five enemies spawn on random empty tiles, walk in a straight line and reverse on hitting a wall or bomb. Fire kills enemies and the player; touching an enemy kills the player. When every player is dead the round restarts with a new map. Esc or closing the window quits.

The assignment brief (Grau A) lives outside the repo, in `../EnunciadoGrauA-Jogo.pdf`. Required items not done yet: time-based sprite-sheet animation (the player sheet only switches row by direction; column 0 is always used) and background layers/parallax (`assets/background.png` is not loaded). A config file is recommended but absent.

## Build & run

Nix (preferred on Linux; a local, gitignored `.envrc` with `use flake` lets direnv load the dev shell automatically):

```sh
nix build            # builds ./result/bin/openbomber
nix run              # build and run
nix develop          # dev shell with cmake, clangd, glfw, glm, libGL, and stb on CPATH
nix build .#windows -o result-windows   # cross-compiles with MinGW-w64
wine result-windows/bin/openbomber.exe  # run from the repo root
```

- `flake.nix` builds both packages with `mkOpenbomber targetPkgs`; `packages.windows` passes `pkgsCross.mingwW64`. The Windows build drops `libGL` (CMake finds `opengl32`) and overrides `glm`'s `meta.platforms`, because nixpkgs doesn't mark it available on Windows. `bin/` gets the `.exe` plus Nix-symlinked DLLs (`glfw3.dll`, `libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libmcfgthread-2.dll`); copy with `cp -L` to take it to a real Windows machine, together with `assets/`.

Plain CMake (inside the dev shell or with deps installed):

```sh
cmake -B build
cmake --build build
./build/openbomber
```

- Run the binary from the repository root: sprites are loaded from relative paths like `assets/player.png`, and the Nix package installs only the binary, not `assets/`.
- Outside Nix, CMake falls back to `FetchContent` to download GLFW 3.4 and GLM 1.0.1. The Nix build disables network fetching and forces `find_package`.
- `stb` (nothings/stb) is supplied only by the flake via `CPATH`; CMake does not know about it. A non-Nix build needs `stb_image.h` on the include path some other way.
- `.devcontainer/` provides a Debian container with Nix (flakes enabled) that pre-builds the dev shell.
- `setPath.bat` is a Windows helper that adds MSYS2 UCRT64 and CMake to `PATH` for building on Windows.

clangd reads `build/compile_commands.json` (generated by `cmake -B build`) and must run inside the dev shell to find Nix-provided headers like GLM and stb. Its diagnostics often lag behind header edits; trust the compiler output.

There are no tests or linters configured.

## Architecture

Ports and adapters:

- `src/game/` is the domain and must not include GLFW/GL (GLM is fine). It defines the ports `Renderer` (`draw(const Game &)`) and `Controller` (`update`, `isDown`, `isPressed` over `ControllerAction`), plus `Game`, `Map`/`MapTile`, `Player`, `Enemy`, `Bomb`, `Fire` and `Hitbox`.
- `Game::run` is the loop: compute `dt` with `steady_clock`, `controller.update()`, then `updateBombs`, `updateFires`, `updateEnemies`, `handleMovement`, `handleFireCollisions`, `handleEnemyCollisions`, `handleBombPlacement`, `renderer.draw(*this)`, and `reset()` once all players are dead. There is no frame cap; pacing comes from vsync (`glfwSwapInterval(1)`).
- Rounds: the constructor relies on `Map`'s default size (19×19) and calls `startRound()`, which creates the player at `(1,1)` and spawns the enemies on the current map. `reset()` clears the entity vectors, assigns a fresh `Map()` and calls `startRound()`.
- The map grid only holds terrain (`MapTileType`: `EMPTY`, `UNBREAKABLE_WALL`, `BREAKABLE_WALL`). Players, enemies, bombs and fires live in vectors on `Game`. Positions are `glm::vec2` in tile units (top-left corner of the sprite), with y growing downward.
- Collision is AABB via `Hitbox` (min/max corners; `intersects` is strict, so touching edges don't collide). `Player` and `Enemy` keep a hitbox inset 0.1 from their 1×1 tile; bombs, fires and tiles use the full tile. Movement projects the hitbox at the next position and cancels the move on collision. `Game::isBlocked(current, next)` checks non-empty tiles and bombs; a bomb the entity already overlaps is ignored, so the player can walk off a bomb it just placed. `handleMovement` still has its own copy of that check.
- `src/infra/opengl/` holds the adapters. `GlfwPlatform` owns GLFW, the window and the GL context, creates `GlController` and `GlRenderer` after them and destroys them before (explicitly, via `unique_ptr::reset`). Headers only forward-declare `struct GLFWwindow`.
- `GlController` maps keys to actions in a static `KEY_BINDINGS` table, polls events in `update()`, and keeps current/previous maps so `isPressed` is an edge trigger.
- `GlRenderer` uses one shader program and one unit quad (VAO/VBO, `GL_TRIANGLE_FAN`). The orthographic projection spans the map size in world units and ignores the window aspect ratio, so the 19×19 map is stretched on the 800×600 window. Each sprite is placed with a `model` translate. Draw order: map, bombs, fires, enemies, players. The vertex shader takes `frameOffset`/`frameSize` uniforms in UV space to cut a frame out of a sprite sheet: most sprites use the whole texture; `player.png` is a 2×4 sheet whose row is picked by `Direction`. Alpha blending is on and textures use `GL_NEAREST`.
- `Sprite` holds the image path, size and GL texture id; `GlRenderer` keeps one `Sprite` per `MapTileType` plus player, bomb, fire and enemy sprites, and loads them in its constructor. Its destructor deletes only the tile and player textures.
- `main.cpp` is the composition root: builds the platform (800×600 window), injects its controller/renderer into `Game`, and turns exceptions into an error message and exit code 1.

## Conventions

- Every class has a `.h`/`.cpp` split, except the header-only port interfaces (`Controller`, `Renderer`). `CMakeLists.txt` globs `src/*.cpp` recursively (with `CONFIGURE_DEPENDS`), so new `.cpp` files are compiled automatically.
- Include roots are `src/`, `include/`, and `include/glad/`, so includes are written relative to `src/` (e.g. `#include "game/map.h"`).
- File names are kebab-case (`gl-renderer.cpp`), classes PascalCase, enum values UPPER_SNAKE_CASE. Gl adapters are prefixed `Gl`/`Glfw`.
- Free helper functions in a `.cpp` are forward-declared just above the method that uses them and defined after it. They have external linkage, so names must be unique across files (hence `createHitbox` in `player.cpp` and `createEnemyHitbox` in `enemy.cpp`).
- Randomness uses `rand()` with no `srand`, so map, spawns and enemy directions repeat between runs.
- GLAD is vendored: `common/glad.c` plus headers in `include/glad/`. `<glad/glad.h>` must be included before `<GLFW/glfw3.h>`; they are separated by a blank line so clang-format doesn't reorder them.
- `STB_IMAGE_IMPLEMENTATION` is defined once, in `gl-renderer.cpp`.
- Art lives in `assets/` as `.aseprite` sources next to exported `.png` files: 32×32 tiles and sprites, plus the 64×128 `player.png` sheet (`background.png` is not used yet).
